# job-gate

## Inputs

- Workspace `$JOB_AGENT_HOME` or `~/.job-agent/`: `profile/preferences.yaml`, the newest `state/scan-*.json` (or one the user names), `state/first-seen.json`, and the tracker.
- Tracker: CSV through `../tracker/scripts/tracker_csv.py --file <csv_path> find|count`, or the Notion or Sheets backend described in the `tracker` skill.
- The queue: `state/queue.json` through `scripts/apply_queue.py` (this skill's folder).

## How to run it

1. For each scan item, read the employer's live posting (step 2 below) and the prior-application sources (step 10), and write what you found into the item: `req_id`, `term_text`, `pay_text`, `location`, `work_mode`, `employer_published` and `employer_date_source`, `levels_hourly` and `levels_note`, `genai_restricted` and `genai_quote`, `prior_check`, `referral`, `prestige` or `step_up` with `step_up_reason`, `fit`, `jd_path`.
2. Run `python3 scripts/gate.py --prefs <workspace>/profile/preferences.yaml --scan <scan file> --tracker <csv_path> --queue <workspace>/state/queue.json --write-queue`. It applies the rules below in order, the same way every run, adds passes (and dropped siblings) to the queue, and prints JSON. Add `--report` for the plain report. With a Notion or Sheets tracker, leave out `--tracker`, apply dedupe and caps by hand with the same rules, and pass the rest to the script.
3. Read the result. Anything it could not judge (a borderline role, a step-up call) you decide, write the reason into the item, and run it again.

## Gate, in order (each default is configurable in preferences)

1. **Title first.** Keep when the title matches a `target_roles` entry or a close synonym; cut when it contains an `exclude_title_words` entry. Judge role type from the title before reading anything else.
2. **Read the full posting**, not the card preview. Read all of it, including the fine print at the end: that is where GenAI rules and term dates sit. Open the employer's live posting (the ATS page the aggregator links to) in its own tab (background, one page id). Pull: requisition ID, term or start date, pay range, location and remote policy, and any statement asking applicants not to use generative AI. Aggregator pages are not enough: JobRight tags skills like "AI Tools" that are not a policy, and its pages list the user's network contacts. Save only the employer's job description text to `state/jd/`, never the aggregator page. If the only apply link goes to linkedin.com or another social site, never open it: search the company's own careers page for the same title or req ID and use that posting, or cut the job with reason `linkedin_only` and list it for the user.
   **Role fit.** The title decides role type before anything else. `role_fit.title_overrides` (for example "Software Engineer") keep a title in even on a team whose flavor is in `role_fit.cut_title_words`; note the team flavor, never cut for it. `role_fit.tailored_title_words` mark roles that need a tailored copy. Obvious role cuts are counted, not listed.
3. **Term.** For internships a stated term must match `term`. A posting with no term follows `term_missing`: `near_miss` (default) or `pass` (report the missing term as a fact, never as the reason to cut).
   **Freshness, two checks.** A posting passes only when (a) it was first seen within `freshness.first_seen_hours` (default `max_posting_age_days` x 24; JobRight ids carry their first-seen time, see `job-scan`) AND (b) the employer's own first-published date, when the posting or the ATS job API gives one, is within `freshness.employer_max_days`. Where to read it: Ashby `publishedAt`, Greenhouse `first_published`, Workday `postedOn` ("Posted 30+ Days Ago" counts), Lever `createdAt`, or a "posted N days ago" line. Either check failing is `REPOST`, cut with the date, even when the aggregator shows it as new: aggregators bump old postings with a fresh publish time. Sources in `freshness.exempt_sources` (newsletters whose drops are days old by design) skip check (a).
4. **Pay.** Compare the midpoint of the posted range with `pay_floor` in the same units. Convert with 2080 work hours a year: hourly = yearly / 2080, and monthly pay is yearly / 12 (so hourly = monthly x 12 / 2080). If the live posting has no pay either, keep the job as a near miss with reason `pay not posted`. Missing pay on an aggregator card is not a cut until the live posting is checked; follow `missing_pay`.
   - `pay_floor.lookup: levels_fyi`: with no posted pay, look up the company's recent intern pay on levels.fyi (read the public page; do not open a tab per company if one lookup page serves all), and pass it as `levels_hourly` with a note of the year, city and number of entries (`levels_note`). At or over the floor passes on that number.
   - `pay_floor.step_up_route: true`: under the floor, or no data, passes only as a clear step up from where the user is now (`prestige`). Write the route and the reason: what an engineer or recruiter would recognize, not a valuation alone. The gate puts the route on the queue entry (`pay_route`).
5. **Location.** Must match `locations`, or be remote when `remote_ok`. `relocate_ok` only answers relocation questions on forms; it does not widen this gate. With `work_mode.remote_requires_prestige: true`, remote passes only at a company in the user's prestige tiers.
6. **Prestige.** `prestige.tiers` ranks companies; `prestige.require: true` makes it a gate. Judge an unfamiliar company before cutting it: look up funding, the engineering domain and the pay, and write the evidence into `step_up_reason`. Never rank by name recall alone.
7. **Skip list.** Cut companies in `companies_to_skip`.
8. **GenAI restriction.** There is no ban list: the job description decides. If the posting restricts generative AI in applications (in the JD, the form, or the fine print), set `genai_restricted: true` with the exact quote. `genai_restriction: flag` (default) fills it as usual and flags it on the queue entry, the run report and the ready banner, so the user decides before submitting; a flagged form is never auto-submitted. `genai_restriction: skip` cuts it with reason `genai_policy` and lists it. Older profiles with `skip_if_genai_banned: true` mean `skip`.
9. **Dedupe.** Key is company plus requisition ID (never company alone). With no req ID, use company plus normalized title plus link. Cut if the tracker already has the key in any status, or the queue holds it in any state (a `DROPPED` entry is never re-added). A later Rejected on the same req overrides an older Assessment. A receipt for a different req at the same company does not mean this one was applied to; say which req the user already holds.
10. **Prior application check (fails closed).** Before a posting can pass, check that the user has not already applied to this req, in every source in `prior_check.sources`, and record each as `clear`, `found` or `error` in `prior_check`:
    - `gmail`: search with the bare company name first, with `in:anywhere` (Promotions and Spam too), never a sender domain or a keyword-only query, then the req ID and title. A receipt is proof the user applied; no receipt is not proof they did not.
    - `tracker`: find by company and req ID.
    - `simplify` (if the user has the Simplify extension): applications sent through it often send no email. On the posting tab, read its shadow roots: `evaluate_script` over `document.querySelectorAll('[id*=simplify],[class*=simplify]')`, each element's `shadowRoot.textContent`, looking for "applied" text with a date.
    - Portals whose receipts name no role (Google careers, for one) show "You submitted this application on <date>" on the posting's own apply page; read it there.
    If any source cannot run, the posting is not a pass this run (`prior_check_failed`; it is retried next run). A connector error is not proof the connector is down: a wrong argument name often returns a bare "tool execution failed". Call one no-argument tool on the same server (for example a label list) before calling it dead.
11. **Referrals.** Search email and the tracker notes for a referrer or a referral link for this company. A referral link: apply through it (`referral: {state: link, link}`). Only a contact: answer the referral question with Employee Referral and their name and email (`state: contact`). A referral ask still waiting on a reply: `state: pending`; the entry is queued as `WAIT-REFERRAL` and not filled until it resolves.
12. **Caps and siblings.** Count tracker rows for the company within its window (`per_company` override or `per_company_default`; `window_days` means rolling, `--since` on the CSV script). Several open roles at one company: rank them by fit to the user's resume, then pay, name the best before spending a capped slot, and queue only the best `caps.best_per_company` (default 2) that fit under the cap. The rest are recorded in the queue as `DROPPED: <why>`, so they are never re-added.

Near misses are not queued. List each one in the report so the user can add it. When a posting is close, cut it: no queue entry beats a weak application.

## Output

- `state/queue.json` (`apply_queue.py`): `{"entries": [...], "removed": [...]}`. Each entry: `{job_key, company, title, req_id, link, apply_url, ats_guess, fit_notes, jd_path, state, pay_route, flags, referral}`. States: `QUEUED`, `WAIT-REFERRAL`, `FILLED`, `NEEDS YOU: <reason>`, `DROPPED: <reason>`. An entry leaves the queue only with a receipt (`apply_queue.py remove --receipt <message id>`), never because a run ended. An older plain-list `queue.json` is read as `QUEUED` entries. Save each full job description to `state/jd/<job_key>.txt` and set `jd_path`.
- Report every run, empty or not (`gate.py --report` prints it): how many postings were scanned and the window covered (back to where the last scan ended), then three groups, each line with the post time, link and pay:
  1. Passes: new, apply.
  2. Already applied or possible duplicate: passes the gates but a receipt, tracker row or banner matches; say which.
  3. Near misses: in-scope roles cut by pay, term, location, work mode or prestige, with the number or fact that failed.
  Then cuts by gate with counts (reposts with their first-seen or publish date), postings whose prior-application check could not run, dropped siblings, and "N obvious role cuts, not listed".
